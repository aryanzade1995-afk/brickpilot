# Formstead

Formstead is a residential **concept and feasibility studio** for villas and
bungalows. A user enters plot dimensions, setbacks, rooms, floors and a design
character; the app creates a deterministic 2D plan, checks it, derives a 3D
building from that same plan, estimates a cost band and exports a report.

The plan is generated by local TypeScript geometry and rules. Image models are
optional and are used for architectural inspiration and presentation renders,
**not** for deciding room coordinates, door positions or structural geometry.
Outputs are concepts, not permit or construction drawings; a licensed architect
and engineers must verify them before use.

## Start here

Requirements: Node.js 22 or newer and npm. The app works without AI keys or a
Supabase account; those integrations are optional.

```bash
npm ci
npm run dev       # Vite web app, normally http://localhost:3000
                  # Node render/interior proxy, normally http://localhost:8787
```

Vite may select another port if 3000 is occupied. To check the project:

```bash
npm test          # deterministic engine and geometry tests
npm run build     # TypeScript check + production bundle
npm run lint      # oxlint
```

To serve the built app and API from one process:

```bash
npm run build
npm start        # normally http://localhost:8787
```

`npm run dev:web` and `npm run dev:proxy` start the two development processes
separately. [`vite.config.ts`](vite.config.ts) proxies `/api` to the Node server.
[`scripts/dev.mjs`](scripts/dev.mjs) starts both together.

## What the user sees

| Route | Purpose |
| --- | --- |
| `/` | Landing page |
| `/workspace` | Eight-step brief: project, site, household, levels, rooms, style, entry, review |
| `/workspace/directions` | Choose from up to four validated exterior directions and optionally upload a reference image |
| `/workspace/plan` | Per-floor SVG drawing, room schedule, validation and cost summary |
| `/workspace/massing` | Interactive Three.js building, layer controls and furnished dollhouse view |
| `/workspace/render` | Geometry-conditioned building concepts and room interior renders |
| `/workspace/report` | Project summary and PDF download |
| `/designs` | Saved projects when Supabase is configured and the user is signed in |

Routes are declared in [`src/main.tsx`](src/main.tsx); the workspace navigation
is in [`src/components/WorkspaceTabs.tsx`](src/components/WorkspaceTabs.tsx).
The brief editor is [`src/routes/Brief.tsx`](src/routes/Brief.tsx) with step
controls in [`src/routes/brief/steps.tsx`](src/routes/brief/steps.tsx).

## How a design is made

```text
Brief (user inputs, Zod schema)
  -> CanonicalModel (oriented plot, buildable envelope, floor programmes)
  -> deterministic plan search (plate, rooms, walls, doors, windows, stairs)
  -> mandatory validation
  -> Design (one source for 2D drawing, 3D building, costs and report)
  -> DesignDNA exterior variants (same verified plan)
  -> optional image renders
```

1. [`src/lib/model/brief.ts`](src/lib/model/brief.ts) defines the editable
   `Brief` and defaults. [`src/lib/model/canonical.ts`](src/lib/model/canonical.ts)
   compiles it into a `CanonicalModel`: plot coordinates, setbacks, floor-by-floor
   room requirements, minimum/target/max areas and desired relationships.
   Distances in the plan model are integer **millimetres**; room areas are m².
2. [`src/lib/engine/generate.ts`](src/lib/engine/generate.ts) selects a supported
   plate family and seed, asks the planner for candidates and keeps a candidate
   that passes mandatory checks. Its four actual plate families are
   `rectangular`, `stepped`, `l-shape` and `courtyard`. The many labels in
   [`src/lib/engine/massing/types.ts`](src/lib/engine/massing/types.ts) map to
   these families; they are not separate geometry algorithms.
3. [`src/lib/engine/planner/`](src/lib/engine/planner/) owns the coordinates:
   `program.ts` normalizes requirements and sizes the stair/site;
   `layout.ts` searches plates and places rooms; `elements.ts` constructs
   walls, columns, beams, openings and shafts; `index.ts` assembles floors and
   reachability; `validate.ts` checks the finished plan.
4. [`src/lib/rules/index.ts`](src/lib/rules/index.ts) combines mandatory plan
   findings with broader planning, geometry, daylight and façade findings.
   `hardChecksPass` is the gate for offering directions and showing a verified
   plan. A failed brief is reported to the user rather than presented as valid.
5. [`src/lib/engine/designDna.ts`](src/lib/engine/designDna.ts) derives seeded
   exterior traits such as composition, entrance, roof, balcony, window treatment
   and materials. [`src/lib/engine/variation.ts`](src/lib/engine/variation.ts)
   scores novelty and picks different-looking directions over the **same plan**.
   [`src/lib/engine/facade/grammar.ts`](src/lib/engine/facade/grammar.ts) anchors
   decorative features to real building faces and checks their placement.

The Style step separates **typology** (villa or larger villa), **massing**
(structural plate choice) and **character** (materials, roof and façade language).
Character themes live in [`src/lib/model/themes.ts`](src/lib/model/themes.ts).
`style.diversity` controls exterior variation; it does not authorize changes to
the pinned room layout. The same brief and seed reproduce the same design.

### Early plot fit feedback

[`src/lib/engine/planner/fit.ts`](src/lib/engine/planner/fit.ts) runs the
planner's minimum-size plate search while the user changes plot dimensions,
setbacks, floors, rooms or massing. The message appears beside those controls
through [`FitNotice.tsx`](src/routes/brief/FitNotice.tsx). It answers whether the
requested minimum room sizes **can fit** the selected plot. It is a precheck:
door access, complete geometry and all other mandatory rules are checked after
generation. Do not treat a green precheck as final plan approval.

### Plan and 3D stay linked

[`src/lib/engine/types.ts`](src/lib/engine/types.ts) defines `Design` and its
`FloorPlan` objects: real room rectangles, footprint blocks, walls, openings,
stairs and structural elements. [`src/lib/draw/FloorDrawing.tsx`](src/lib/draw/FloorDrawing.tsx)
draws those objects in 2D. [`src/lib/three/buildMassing.ts`](src/lib/three/buildMassing.ts)
converts the **same** footprint, wall and opening data into 3D boxes and roof
prisms; [`src/lib/three/MassingScene.tsx`](src/lib/three/MassingScene.tsx)
renders them. [`src/lib/three/buildDollhouse.ts`](src/lib/three/buildDollhouse.ts)
and `DollhouseScene.tsx` create a furnished cutaway view. Exterior variation
can change presentation details, but it must preserve plan openings and rooms.

This experimental branch adds seed-driven roof geometry to `DesignDNA`:
slim, deep-eave and raised-edge profiles; constrained ridge direction,
pitch and mono-slope orientation. The roof still caps the verified floor
footprint. A cross ridge is allowed only on near-square blocks, and all
variants retain identical room, wall, door, window and stair coordinates.
The roof variation follows the footprint/roof-form variation ideas in
[SYNBUILD-3D](https://github.com/kdmayer/SYNBUILD-3D) and its
[paper](https://arxiv.org/abs/2508.21169). No SYNBUILD dataset or generator
code is bundled with Formstead.

Validation includes requested-room counts and sizes, room overlap and plate
coverage, setbacks, door width and placement, room reachability, stair/lift
continuity, opening/column conflicts and vertical support. Attached-bath doors
may use the bedroom's vertical shared wall; ordinary internal room-to-room
doors may not. The key checks are in `planner/validate.ts` and `rules/index.ts`.

## Rendering and reference images

There are two different image flows. Neither supplies the source geometry.

**Building concepts:** [`src/routes/Render.tsx`](src/routes/Render.tsx) captures
fixed views of the Three.js model and a plan reference, then builds prompts from
the brief, theme, `DesignDNA` and selected view. [`src/state/render.ts`](src/state/render.ts)
sends the reference and prompt to `POST /api/render`; the Node server calls
Gemini when `GEMINI_API_KEY` is configured. Without the key, it returns the
source reference image as a fallback. Image outputs are presentation concepts,
so verify them against the actual 2D/3D geometry.

**Inspiration image:** On Directions, a PNG/JPEG/WebP image can be analyzed by
`POST /api/inspiration` into bounded style preferences. These influence
`DesignDNA` and may accompany the final building render. The image cannot move
rooms, doors, windows or structure. Style analysis requires a Gemini key; if it
fails, the image can still be used as a render reference.

**Interior concepts:** [`src/components/InteriorStudio.tsx`](src/components/InteriorStudio.tsx)
captures room views and edge/depth/beauty maps from the generated geometry.
[`src/lib/render/interiorPrompt.ts`](src/lib/render/interiorPrompt.ts) writes the
room prompt. `POST /api/interior` streams progress and the output image. The
default provider is local ComfyUI with an SDXL/Canny workflow at
[`server/workflows/interior-sdxl.json`](server/workflows/interior-sdxl.json).
The provider registry is [`server/providers/index.mjs`](server/providers/index.mjs)
(`comfyui`, `gemini`, `mock`). An unavailable configured provider falls back to
the mock result, which returns a reference rather than a generated interior.

The Node API and production static server are in [`server/index.mjs`](server/index.mjs):

| Endpoint | Use |
| --- | --- |
| `GET /api/render/health` | Building image-model availability |
| `POST /api/render` | Building image edit from the captured model and prompt |
| `POST /api/inspiration` | Classify a reference image into style preferences |
| `GET /api/interior/health` | Interior provider availability |
| `POST /api/interior` | Stream interior render progress and result |

## Configuration

Copy [`.env.example`](.env.example) to `.env.local` for optional browser-side
Supabase settings. Copy [`server/.env.example`](server/.env.example) to
`server/.env` for local server settings. Both local files are gitignored.

| Variable | Used by | Purpose |
| --- | --- | --- |
| `VITE_SUPABASE_URL`, `VITE_SUPABASE_ANON_KEY` | Vite client | Optional sign-in and saved designs |
| `GEMINI_API_KEY` | Node server | Building renders and inspiration analysis; also Gemini interiors if selected |
| `RENDER_MODEL`, `INSPIRATION_MODEL` | Node server | Optional Gemini model overrides |
| `RENDER_MOCK=1` | Node server | Return the building reference instead of calling Gemini |
| `RENDER_PROXY_PORT` | Node server + Vite proxy | Local API port (default `8787`); production uses `PORT` |
| `INTERIOR_PROVIDER` | Node server | `comfyui` (default), `gemini` or `mock` |
| `COMFYUI_URL`, `SDXL_CKPT`, `CN_CANNY_MODEL` | ComfyUI provider | Local service URL and installed model filenames |
| `INTERIOR_*`, `CN_CANNY_*` | ComfyUI provider | Optional sampling and conditioning overrides; see `server/.env.example` |

Only `VITE_*` variables are bundled into the browser. Keep `GEMINI_API_KEY`
server-side. To use accounts, run [`supabase/schema.sql`](supabase/schema.sql)
in a Supabase project, set the two `VITE_SUPABASE_*` values and enable Email
auth. The app remains usable signed out. Supabase saves the brief plus pinned
direction, then regenerates geometry, validation and cost on load; it does not
store the generated images as part of a design.

[`src/state/studio.ts`](src/state/studio.ts) owns the working brief, candidate
directions, pinned direction and generated result. It persists the brief and
pinned choice in browser local storage under `brickpilot.studio`; changes to the
brief invalidate cached geometry. [`src/state/designs.ts`](src/state/designs.ts)
handles optional Supabase projects. Render and interior images live in ephemeral
stores ([`render.ts`](src/state/render.ts), [`interior.ts`](src/state/interior.ts))
because the base64 data can be large. The Report page can include current
generated images in its PDF, but those images are not persisted across reloads.

## Costs, reports and deployment

[`src/lib/cost/index.ts`](src/lib/cost/index.ts) estimates an advisory cost
band from the generated design. [`src/routes/Report.tsx`](src/routes/Report.tsx)
builds the report UI and loads [`src/lib/report/buildPdf.ts`](src/lib/report/buildPdf.ts)
for PDF export. The PDF includes the brief, floor drawings and room schedules,
validation, costs and available images.

[`render.yaml`](render.yaml) deploys one Render web service. Its build command
installs dev dependencies and builds the SPA; `npm start` serves `dist/` with
client-route fallback and handles `/api` on the same origin. Set secrets and
optional Supabase values in the hosting environment, not in committed files.

## Tests and source data

`npm test` runs [`scripts/test-planner.mjs`](scripts/test-planner.mjs) and
[`scripts/test-generation.mjs`](scripts/test-generation.mjs). They exercise
determinism, requested-room preservation, openings, access and structural
checks, 2D-to-3D consistency, exterior variants and the early fit indicator.
`npm run build` is the TypeScript/build gate. `npm run lint` checks the source.

The runtime has **no dataset download, model training or 3D asset ingestion**.
Room-area presets are in `src/lib/model/canonical.ts` and minimum dimensions in
`src/lib/rules/index.ts`. [`scripts/resplan_stats.py`](scripts/resplan_stats.py)
can analyze an independently obtained ResPlan ZIP for offline reference
statistics. The committed [`scripts/resplan_stats.json`](scripts/resplan_stats.json)
explicitly contains **provisional reference values** (`plans_used: 0`), not
measurements extracted from that dataset. No ResPlan or SYNBUILD geometry is
shipped or read by the app.

## Where to change things

| Goal | Start with |
| --- | --- |
| Add a user requirement or brief control | `src/lib/model/brief.ts`, `src/routes/brief/steps.tsx`, `src/lib/model/canonical.ts` |
| Change plot/room fit feedback | `src/lib/engine/planner/fit.ts`, `src/routes/brief/FitNotice.tsx` |
| Change room placement or door access | `src/lib/engine/planner/`, then `src/lib/rules/index.ts` and planner tests |
| Change exterior variation or façade details | `src/lib/engine/designDna.ts`, `variation.ts`, `facade/grammar.ts` |
| Change 2D drawing or 3D geometry | `src/lib/draw/FloorDrawing.tsx`, `src/lib/three/buildMassing.ts`, `MassingScene.tsx` |
| Change prompts or image providers | `src/routes/Render.tsx`, `src/lib/render/`, `server/index.mjs`, `server/providers/` |
| Change saved designs | `src/state/studio.ts`, `src/state/designs.ts`, `supabase/schema.sql` |

Keep the verified `Design.floors` geometry as the common source for drawing,
Three.js and reporting. When changing the planner, run the geometry and
validation tests and check that generated directions still pass mandatory rules.
